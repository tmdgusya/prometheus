prometheus — 절차의 불을 ZCode /goal에 위임하다

prometheus는 더 이상 자체 게이트 엔진을 가지지 않는다. 스토리 분해는 에이전트가, goal 세팅은 사용자가, 완료 판정은 ZCode 런타임이 매 턴 내린다. 이 페이지는 그 삼각 구조를 한눈에 보여준다.

goals.py 폐기됨 검증 게이트 → ZCode /goal 에이전트 = 설계자, 사용자 = 세팅자 GLM-5.2 효과 미측정
이전 버전에서의 정정: 예전 시각화는 goals.py 상태머신을 중심으로 그려졌다. 그러나 goals.py는 "에이전트가 자발적으로 호출해야만 작동"하는 소프트 입구 문제가 있었고, ZCode /goal이 매 턴 런타임 강제를 제공함이 확인되어 폐기되었다. 이 페이지는 그 결정 이후의 구조를 묘사한다.

Section 01

01삼각 역할 모델 — 누가 무엇을 하는가

prometheus의 핵심 설계 결정: 검증 강제를 세 주체에게 분산한다. 에이전트는 게이트를 만들지 못하지만 좋은 goal 문장을 설계할 수 있고, 사용자는 그것을 복사해 /goal로 세팅하며, ZCode 런타임은 매 턴 끝에 verifier를 돌려 완료를 판정한다.

에이전트 (prometheus)

§1로 맥락 확보 후 독립 단위로 스토리 분해. 각 스토리를 검증 가능한 /goal 문장으로 변환해 사용자에게 제시. 직접 /goal을 세팅하지 못함 — chat input에 접근 불가.

사용자

에이전트가 제시한 문장을 복사해 chat input에 입력. 첫 스토리는 /goal, 이후 스토리는 /goal replace. 이 단계가 거쳐야만 런타임 강제가 시작됨.

ZCode 런타임

세팅된 goal에 대해 매 턴 끝에 verifier 실행. 에이전트의 "완료" 선언과 무관하게 판정. proxy signal(테스트만 통과 등) 거부, 불확실성 = 미완료.

Section 02

02goals.py vs ZCode /goal — 강제 수준의 차이

둘 다 "증거 없는 완료 거부"를 목표로 했지만, 강제가 발생하는 층이 다르다. goals.py는 가장 결정론적 장치의 입구가 가장 결정론적이지 않은 층(에이전트 자발성)에 있었다. /goal은 입구 자체가 없다.

✗ goals.py (폐기됨)

소프트 입구 — 에이전트가 안 부르면 끝

  • 게이트는 에이전트가 goals.py checkpoint를 자발적으로 호출해야 작동
  • 한 번도 안 부르면 → 하드 게이트가 작동할 기회 자체가 없음
  • 상태는 ./.prometheus/ 파일 — 세션 너머 지속은 됨
  • 완료 선언은 여전히 에이전트 몫 (게이트가 거부하긴 함)
이 프로젝트에서 실제 관찰:
에이전트가 분해→검증 게이트를 밟아야 할 자리에서
goals.py를 한 번도 부르지 않고 작업을 끝냄.
→ 하드 게이트, 무력.
✓ ZCode /goal (현재)

입구 없음 — 런타임이 매 턴 끼어듦

  • 사용자가 한 번 세팅하면 매 턴 끝에 런타임이 verifier 실행
  • 에이전트가 "완료" 선언 불가 — 시스템이 판정
  • 증거 없으면 자동으로 다음 턴 진행
  • 불확실성 = 미완료 취급
에이전트의 역할은 축소:
좋은 goal 문장을 설계해 사용자에게 제안하는 것.
강제 자체는 더 이상 prometheus의 몫이 아님.

Section 03

03순차 multi-story 루프 (SKILL.md §2-D)

스토리가 2개 이상일 때의 실행 흐름. 각 단계마다 누가 하는지 색으로 표시 — 에이전트 · 사용자 · 런타임.

1

스토리 리스트를 /goal 문장으로 변환에이전트

§1로 분해한 전체 스토리를 §2-C 형식(검증 명령 + 예상 출력 포함)의 /goal 문장으로 변환해 사용자에게 한 번에 제시.

2

첫 스토리를 /goal로 세팅사용자

에이전트가 제시한 첫 문장을 복사해 chat input에 /goal ... 입력. 이 순간부터 런타임 강제가 시작.

3

그 스토리만 작업에이전트

활성 goal만 작업. 다른 스토리는 손대지 않는다. 증거를 도구 결과로 생산하며 진행.

4

매 턴 끝에 verifier 실행런타임

에이전트 완료 선언과 무관하게, 시스템이 prompt-to-artifact 체크리스트로 모든 요구사항이 증거로 커버됐는지 평가. 통과 못 하면 자동 다음 턴.

5

달성 알림 → 다음 스토리 /goal replace사용자

시스템이 goal 달성을 알리면, 에이전트가 다음 스토리 문장을 제시하고 사용자가 /goal replace ...로 교체.

★

마지막 스토리 = end-to-end 검증런타임

마지막 스토리는 반드시 통합 검증. 전체 범위가 증거로 커버되어야 런타임이 통과시킴.

단일 단계 작업은?

분해 결과 스토리가 1개뿐이면 루프를 건너뛴다 — goal 하나로 충분. 단, §1 맥락 확보는 단일 단계에서도 버그 원인 파악 등에 유용할 수 있어 건너뛰지 않는 게 좋다.

TodoWrite는 어디에?

진행 상황을 사용자에게 보여주기 위해 TodoWrite로 병행 기록할 수 있다. 하지만 완료 판정은 TodoWrite가 아니라 /goal 런타임이 내린다 — TodoWrite는 발표용이지 게이트가 아니다. 헷갈리지 말 것.

Section 04

04좋은 /goal 문장 — 에이전트의 진짜 가치

에이전트가 게이트 강제를 런타임에 넘겼다면, 남는 가치는 verifier가 판정할 수 있는 goal 문장을 설계하는 것이다. 모호한 goal은 verifier까지 속여 자기기만이 된다.

✓ 검증 가능
/goal auth/login.ts:42의 EAUTH
원인을 수정한다. 검증:
`npm test auth/login` 이 9 passing으로
통과하고, `node repro.js` 가 exit 0으로
종료되며 에러 로그를 출력하지 않는다.

왜 좋은가: verifier가 판정할 객관적 조건(명령 + 예상 출력)을 갖춤. "통과했다"가 아니라 "9 passing"이라 구체적.

✗ 자기기만 위험
/goal 로그인 에러를 우아하게
해결한다.

왜 위험한가: "우아하게"라는 모호어가 verifier까지 속임. 실제론 안 됐어도 "대충 됐다"고 판정날 수 있고, 그게 자기기만.

설계 원칙 (SKILL.md §2-C)

  • 검증 명령을 문장 안에 직접 적는다 — "잘 동작한다"가 아니라 "`npm test`가 9 passing"
  • 예상 출력까지 포함한다 — exit code, 로그 부재, 카운트 등 관측 가능한 형태
  • 모호어를 피한다 — "우아하게", "깔끔하게", "적절히"
  • 한 스토리 = 한 goal — 1차원 목표. "API + UI + 테스트"는 3개 goal

06번들 파일 — 남은 불씨들

goals.py는 사라졌다. 남은 건 두 개의 팩 — 에이전트가 직접 따르는 절차 규율이다. /goal이 커버하지 못하는 영역(조사·렌더 검증)을 채운다.

~/.agents/skills/prometheus/packs/investigation-protocol.txt

디버깅 조사 규율. 재현 → 경쟁 가설 3+ → 가설별 증거 → 전체 인과사슬 → 전후 검증 → 기각한 가설 보고.

~/.agents/skills/prometheus/packs/verification-grounding-pack.txt

렌더 산출물 검증 규율. 실제 렌더러에서 실행 → 출력 관찰 → 수정 → 재실행. 정적 파싱은 well-formed만 확인.
